# Pillar 3.5 — Encoder coverage + bug investigation + crash diagnostics

**Date**: 2026-05-20
**Status**: Spec (pre-implementation)
**Parent pillar**: P3 (RIFE frame interpolation), shipped through P3.4 on `master`
**Successor**: P4 (Anime4K shader upscale) — blocked on this until Pillar 3 verifies on real hardware

---

## 1. Goal

Make Pillar 3 actually deliver smooth motion on real hardware (Abed's Snapdragon X dev box + the typical Intel/AMD/NVIDIA Windows laptop), and fix two specific bugs surfaced during the 2026-05-20 cast test.

End state: Abed can cast anime through Castbooster with the Smooth Motion toggle ON, the RIFE pipeline actually runs, the encoder keeps up in real-time, the app does not crash mid-session, and any failure surfaces a visible message instead of silently demoting to passthrough.

## 2. Background

P3.4 merged on 2026-05-20 (commit `ce4e74b`). 323 unit tests green. First real-hardware test the same evening revealed three independent problems:

1. **Silent crash.** App died twice without writing a "shutting down" log line. Once between 20:42:52 and 20:45:13 (auto-restarted by Chrome NM ping), and again between 20:45:26 and 20:47:14. Log contains no traceback, no exception, no exit reason. Root cause currently undetermined.

2. **Toggle doesn't reach RIFE.** Abed toggled Smooth Motion ON in the picker view, then again in the player view. Both paths produced no observable enhancement on the TV. Proxy log shows `smooth=False chain=noop` on the cast attempt — meaning either `enable_smooth=true` never reached the proxy, or `_build_filter_chain` silently demoted to NoopFilter. Existing log line is too low-resolution to distinguish the two.

3. **Encoder timed out at 12s warming budget.** ffmpeg encoder probe failed all hardware tiers (no NVENC because no NVIDIA driver, no QSV because no Intel chip, no AMF because no AMD chip) and fell back to `libx264` software encoder. The 12s warming budget was insufficient for software encoding to produce a first segment on this hardware. The transcoder gave up and the cast fell back to raw passthrough — meaning Pillars 2/3 contributed nothing to this session, the user got the unmodified original stream.

The root cause of (3) is that Abed's machine is a **Snapdragon X Copilot+ PC (ARM64 Qualcomm Oryon CPU with Adreno X1-45 GPU)** — none of the three x86 hardware encoder vendors our probe tries are present. The Adreno chip has a hardware H.264 encoder that ffmpeg can reach via `h264_mf` (Windows Media Foundation Transform), verified at 2.35× real-time on Abed's hardware. The probe doesn't currently try `h264_mf`.

**Note**: a complementary "lightweight bug-capture toolkit" landed on master as `72436d5` (post-P3.4, pre-this-spec). That commit covers: line-numbered log formatter, tray "Copy diagnostic bundle" menu item, `tail_logs.ps1` helper, and `window.onerror`/`unhandledrejection` hooks in popup + background.js. This spec **does not duplicate** any of those; in particular, Thread 1's Python-side hooks are additive to the existing JS-side ones, and Thread 2's value-logging is additive to the existing uncaught-error capture.

## 3. Scope

### In scope (this spec)

- **Thread 1**: Crash diagnostics (instrumentation, no fix until we know the cause).
- **Thread 2**: Toggle bug investigation (instrumentation in popup + proxy, plus one already-identified silent-fallback fix in `_build_filter_chain`).
- **Thread 3**: `h264_mf` encoder support + bumped SW warming timeout.
- **Thread 4**: Bump default `max_fps` for "Chromecast" model from 30 to 60 so the most common Chromecast (3rd gen, 2018+) actually gets the 24→60 RIFE boost instead of a barely-noticeable 25→30 interpolation.
- **Thread 5**: Server-side migration documented as future work (vault note only, no code).

### Out of scope (carried to other pillars)

- Real GPU benchmarks on GTX 1660 / RTX 3060 (Pillar 3 spec §7 — requires hardware Abed doesn't own).
- Polar.sh wiring for `is_pro()` — Pillar 6.
- Anime4K shader upscale — Pillar 4.
- Frame-lag / GPU-temp based perf watchdog — Pillar 5.
- ARM64-native ffmpeg build — out of scope; `h264_mf` via x86-emulated ffmpeg is sufficient because MF dispatches to native Windows APIs regardless.
- Macs, phones, tablets, Chromebooks — Pillar 6+ or server-side migration.
- Cloud GPU pipeline — see thread 5 backlog.

### Explicit non-goals

- Do NOT attempt to fix the silent crash before instrumentation lands. We need evidence; we have none. The investigation is the deliverable for thread 1, not a fix.
- Do NOT bundle an ARM64 ffmpeg build. `h264_mf` is the right answer for ARM Windows.
- Do NOT change the popup UX or add new toggles. Limited to instrumentation + the one silent-fallback fix.

## 4. Design

### 4.1 Thread 1 — Crash diagnostics

**Problem**: app dies without writing anything to the log. Could be a non-asyncio thread exception, an OS-level kill, an unhandled coroutine exception, a `sys.exit(1)` somewhere, or a hard segfault.

**Approach**: install three exception hooks + boundary logging at process entry/exit. No code change attempts to *prevent* the crash — only to *record* it next time.

**Changes**:

- `app/castbooster/main.py`:
  - Install `sys.excepthook` that logs `logger.exception("FATAL unhandled exception in main thread")` before default exit.
  - Install `threading.excepthook` (Python 3.8+) that logs unhandled exceptions in all non-main threads (the keepalive thread, transcoder side-task threads, pychromecast listener thread).
  - Wrap the entry point in `try/finally` that emits `log.info("castbooster shutdown reason=normal|exception|signal")` on exit, with reason populated from a module-level flag set by the excepthooks.
  - Set `logging.shutdown()` in the finally block to flush all handlers.

- `app/castbooster/proxy.py` (asyncio side):
  - In `main()` or wherever the event loop is created, call `loop.set_exception_handler(...)` to log unhandled coroutine exceptions.
  - Add `log.info("proxy entering main loop")` and a paired `log.info("proxy exited main loop")` around the `loop.run_until_complete` call.

- `app/castbooster/log.py`:
  - Force `logging.StreamHandler.flush()` to be called after every record (subclass the file handler or set `delay=False` + tighter buffering). Trade slight perf cost for not losing the last few lines on crash.

- Manual checks (not code):
  - Open Windows Event Viewer → Windows Logs → Application during the 20:42:52–20:45:13 and 20:45:26–20:47:14 windows. Look for `Application Error` or `.NET Runtime` entries citing `python.exe`. Capture any Faulting Module Name (could reveal a native crash like a Vulkan driver fault).

**Acceptance**: re-run the cast test from 2026-05-20. If the app dies again, the log file MUST contain either a traceback or a "shutdown reason=signal" entry. If neither appears, the crash is OS-level (kill from outside the process) and we move to Event Viewer / sysmon as evidence sources.

### 4.2 Thread 2 — Toggle bug investigation

**Problem**: `smooth=False chain=noop` in the proxy log on a session where the user toggled smooth ON. Three layers could be at fault:

1. Popup UI — toggle didn't actually flip (capabilities probe returned false → hidden; or click handler short-circuited).
2. NM bridge — `enable_smooth` got stripped in popup → background → app.
3. Proxy — received `enable_smooth=true` but `_build_filter_chain` silently fell back (e.g., `video is None` because ffprobe 404'd the source URL).

**Approach**: instrument all three layers BEFORE attempting any fix. Then have Abed reproduce. The log will name the broken layer.

**Changes**:

- `app/castbooster/proxy.py`:
  - `_handle_capabilities`: log the response — `log.info("capabilities: is_pro=%s vulkan_available=%s", ...)`. Today nothing is logged here.
  - `_handle_cast`: log the raw enable_smooth value as received — `log.info("[cast token=%s] enable_smooth_raw=%r", log_token, msg.get('enable_smooth'))`. Coercion to bool happens AFTER the log so we see the wire value.
  - `_handle_set_filter_chain`: same — log raw `msg.get('enable_smooth')` on entry.
  - `_build_filter_chain`: log which branch was taken AND why. Today the function silently returns NoopFilter with no log. Add one log line per branch, naming the branch and the deciding values (`enable_smooth`, `is_pro`, `audio_only`, `video.fps`, `target_fps`). Branches to instrument:
    - `audio_only` branch (Chromecast Audio etc.)
    - `not enable_smooth` branch (user toggle off)
    - `not is_pro` branch (free tier — currently never hits since stub returns True)
    - `video is None` branch (ffprobe failed — the most likely cause for tonight)
    - VFR branch (`video.fps is None`)
    - source≥target branch (source already meets target FPS)
    - rife branch (the happy path — include `source_fps`, `target_fps`, `width`, `height`)

- `extension/popup.js`:
  - After `probeSmoothCapabilities()` returns, `console.log('[castbooster] capabilities:', caps, 'smoothCapabilitiesReady:', smoothCapabilitiesReady)`.
  - Immediately before each `chrome.runtime.sendMessage({ type: 'CAST_NOW', ... })`, `console.log('[castbooster] CAST_NOW smoothMotionPref:', smoothMotionPref)`.
  - Inside both toggle click handlers: `console.log('[castbooster] toggle clicked, was:', smoothMotionPref, '→ will set:', !smoothMotionPref)`.

- `extension/background.js`:
  - In `CAST_NOW`, `console.log('[castbooster] CAST_NOW msg.enable_smooth:', msg.enable_smooth)` immediately on entry.
  - Before sending `cast` to native, `console.log('[castbooster] forwarding enable_smooth to proxy:', !!msg.enable_smooth)`.

**Already-identified fix** (do NOT wait for repro — this is provable from code reading alone):

- `_build_filter_chain` line 190 — when `video is None` AND `enable_smooth=True`, currently returns `(NoopFilter, None)`. The `None` info_message means the popup gets NO indication that smoothness was silently dropped. **Fix**: return a probe-failure info_message:
  ```python
  _PROBE_FAILED_INFO = "Smoothness skipped — couldn't analyze source video"
  ...
  if video is None and enable_smooth and license.is_pro() and not caps.audio_only:
      return FilterChain([NoopFilter()]), _PROBE_FAILED_INFO
  if caps.audio_only or not enable_smooth or not license.is_pro() or video is None:
      return FilterChain([NoopFilter()]), None
  ```
  Order matters — check the "user asked for smooth + probe failed" case BEFORE the catch-all silent fallback.

**Acceptance**: Abed reproduces the cast test with DevTools console open on the popup. We collect both `castbooster.log` and the console log. The combined logs will name exactly which layer is broken. THEN we ship a targeted fix in a follow-up commit on the same branch.

### 4.3 Thread 3 — `h264_mf` encoder support

**Problem**: Abed's Snapdragon X exposes a working hardware H.264 encoder via Windows Media Foundation (`h264_mf`), but `ffmpeg_probe._ENCODER_CANDIDATES` doesn't try it. Probe falls through to `libx264` software, which can't keep up under x86 emulation, transcoder times out at 12s, fallback to passthrough.

Verified: `h264_mf` runtime probe on Abed's hardware produces video at 2.35× real-time. Hardware is real, encoder works, just not wired in.

**Changes** (`app/castbooster/ffmpeg_probe.py`):

- Append `h264_mf` to `_ENCODER_CANDIDATES` after `h264_amf`, before `libx264`:
  ```python
  _ENCODER_CANDIDATES = ("h264_nvenc", "h264_qsv", "h264_amf", "h264_mf", "libx264")
  ```
- Add tier mapping: `_TIER_FOR_ENCODER["h264_mf"] = "mf"`.
- Add decoder pairing: `_DECODER_FOR_TIER["mf"] = ("none",)`. Don't try to pair with d3d11va — matches the 2026-05-17 SW-tier safe default for the same reason (avoid the early D3D11 device-context hang).
- Add warming budget: `_WARMING_TIMEOUT_BY_TIER["mf"] = 6.0` (matches the other HW tiers).
- **Bump SW timeout**: `_WARMING_TIMEOUT_BY_TIER["sw"]` from 12.0 to 24.0. Defense-in-depth — protects users who fall through to libx264 on cold start. 24s is still well under the user's patience threshold for "starting cast" and dramatically reduces false-positive passthrough fallback.

**Tests** (`app/tests/test_ffmpeg_probe.py`):

- `test_encoder_selection_picks_h264_mf_when_no_other_hw` — fake encoder list with `h264_mf` + `libx264` only; expect `accel.encoder == "h264_mf"`, `accel.tier == "mf"`.
- `test_h264_mf_runtime_probe_passes_when_synthetic_encode_succeeds` — mock `subprocess.run` to return code 0 for `h264_mf -frames:v 1` test; expect probe accepts it.

No new gated tests required — `h264_mf` works on every Windows machine with a Vulkan/D3D-capable GPU (so basically every Windows machine made since 2012), but the runtime probe handles real-vs-fake detection automatically.

### 4.4 Thread 4 — Bump `max_fps` for "Chromecast" model from 30 to 60

**Problem**: pychromecast reports `model_name="Chromecast"` for 1st, 2nd, AND 3rd-gen Chromecasts — indistinguishably. Our `receiver_caps.py` conservatively maps that string to `max_fps=30` to protect the oldest hardware. But:

- 1st-gen Chromecast (2013) — 12 years old, nearly extinct in the wild.
- 2nd-gen Chromecast (2015) — 10 years old, also rare.
- **3rd-gen Chromecast (2018)** — the most common device today that reports `model_name="Chromecast"`, supports 1080p60.

Result of the conservative default: even when RIFE works perfectly, `target_fps = caps.max_fps = 30`. RIFE interpolates a 25fps source up to only 30fps — a barely-perceptible difference. The user's stated goal of "at least 60fps" is impossible to meet without changing this.

**Approach**: flip the default to optimistic. Trust the Chromecast to handle a 60fps input (worst case: old hardware silently decodes-and-downsamples to 30fps internally, which is the same end-result as today). No UI toggle, no user-facing decision required.

**Changes** (`app/castbooster/receiver_caps.py`):

- Change the `"Chromecast"` table entry from `max_fps=30` to `max_fps=60`. Keep `max_width=1920, max_height=1080` unchanged (1st/2nd-gen Chromecasts maxed out at 1080p — that part of the conservative default stays correct).
- Update the docstring around line 12 (`Conservative-fallback rule…`) to document the new optimistic default and the reasoning (3rd gen is the modal case, old hardware degrades gracefully).
- Update unit tests in `app/tests/test_receiver_caps.py` — the test expecting `max_fps=30` for `"Chromecast"` flips to expect 60.

**Risk**: 1st/2nd-gen Chromecast users may see playback issues if their hardware rejects the 60fps input outright. **Mitigation**: most Chromecasts cope by decoding at 60 and outputting at 30 internally — visible result identical to today's 30fps cap. If a user reports a hard failure, we add a popup override in a follow-up spec.

**Acceptance** (manual, on Abed's Dining room TV):
- After threads 3 + 4 land, cast a 25fps anime source.
- Check log: `chain=rife` AND `target_fps=60` (new log line in `_build_filter_chain` from thread 2 will show this).
- On the TV: visibly smoother panning + fight scenes than the unmodified source.

## 6. Risks and unknowns

- **The silent crash might be OS-level** (Windows killing python.exe due to Modern Standby, antivirus, or driver issue). In that case the in-process hooks won't catch it. Mitigation: Event Viewer check is the secondary evidence source. If both are silent, we escalate to ProcDump or a similar external watchdog.
- **`h264_mf` quality may differ** from `h264_nvenc`/`h264_qsv`. Media Foundation's quality depends on the underlying driver implementation. Qualcomm's encoder is good but may produce different bitrate/quality trade-offs than Intel QSV. Mitigation: rely on the existing acceptance harness from P2.6; visual comparison if Abed reports artifacts.
- **The "user toggled on but proxy saw false" bug might be a UI-only confusion** — e.g., the toggle was hidden (capabilities probe returned `vulkan_available=false`) and the user thought they toggled but didn't. Logging will clarify; no risk of building the wrong fix because we instrument first.
- **24s warming timeout for SW tier might be too long for impatient users.** Mitigation: most users hit a HW tier (nvenc/qsv/amf/mf) and never see the SW path. The bump only affects users who somehow have NO hardware encoder at all, which is a rounding error on modern Windows.

## 7. Out-of-scope items captured for later

- **Hardware survey**: post-launch, ship a one-time anonymous "what encoder did we pick?" telemetry ping to validate the assumption that >95% of users hit a HW tier. Pillar 6 territory (when telemetry infra exists).
- **`h264_mf` ALSO usable on x86 Windows** — even on Intel/AMD/NVIDIA machines, MF is a fallback if their vendor-specific encoder fails. Already covered by the priority chain (MF comes after AMF before libx264).
- **Hot-swappable encoder probe** — current probe runs once at startup and caches. If a user plugs in an eGPU mid-session, we won't pick it up. Out of scope; user can restart the app.
