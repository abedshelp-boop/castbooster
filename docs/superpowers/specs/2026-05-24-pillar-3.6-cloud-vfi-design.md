# Pillar 3.6 — Cloud RIFE VFI MVP (Single-User, for Abed)

## TL;DR

After the 2026-05-21 multi-vendor pivot, the 2026-05-24 empirical test of ANVIL on
Abed's Snapdragon X Hexagon NPU **falsified** the local-Snapdragon leg of that
plan: ANVIL ran 17× slower than the paper's claim, with no path to 60fps even
after full INT8 + VTCM optimization. We pivot again — this time to **cloud Phase
1 as the only viable universal 60fps path** — and scope tightly to **MVP-for-Abed
(single user) so the feature ships in ~3 weeks instead of ~5 months**.

End-user experience (Abed only, on egydead anime today): click "Cast smooth" in
the castbooster popup, wait ~25-30s for a RunPod RTX 4090 pod to warm, watch
60fps interpolated anime on Chromecast. Pod self-shuts after 10 min idle. Ongoing
cost ~$41/mo at Abed's ~4 hrs/day usage.

This is **NOT** a Phase 2 production architecture. Crunchyroll/Widevine DRM,
multi-user, billing, hot-spare warm pool, and Sentry observability are all
explicitly deferred — each is a known Phase 2 problem with its own design pass.

---

## 1. Empirical findings that drove this design

### 1.1 ANVIL empirical test on Snapdragon X (2026-05-24)

Ran ANVIL-S + ANVIL-M (HuggingFace pre-built ONNX, `D_unet_v3b{s,m}_nomv_1080p`)
on Abed's Adreno X1-45 / Snapdragon X PC via:
- Python 3.12.10 native ARM64 (python.org installer)
- onnxruntime 1.26.0 + onnxruntime-qnn 2.1.1
- QNN EP plugin registered via `ort.register_execution_provider_library`
- `htp_arch=73`, `enable_htp_fp16_precision=1`, `htp_performance_mode=burst`

Measured median 1080p inference:
- ANVIL-S: **1998 ms** (fp16, QNN HTP attempted — silently fell back to CPU on most nodes)
- ANVIL-M: **989 ms** (same path)
- CPU-only baseline: 2771 ms (ANVIL-S), 3136 ms (ANVIL-M)

Paper reference (SM8650 mobile, HTP V75 INT8): 17.0 ms inference, 28.4 ms E2E.

**Best-case realistic projection** on Abed's hardware after full INT8 + VTCM
optimization: 60-90 ms = 11-17 FPS. Still not 60. Possibly 30fps after extensive
engineering. The Snapdragon leg of the 2026-05-21 multi-vendor pivot is dead.

### 1.2 Why no other local path works either

From the 2026-05-24 cloud-architecture research agent run:
- **WebGPU RIFE** — no working port in 2026, ~2-3 month engineering to build one,
  output 15-30 FPS at 720p, not 60.
- **Apple M4 ANE** — 30-45 FPS at 1080p tops, <10% of market.
- **Snapdragon X2 Elite (2026 laptops, 80 TOPS)** — naive scaling gives 5-7 FPS;
  even an 80-TOPS NPU is held back by the same VTCM/quantization issues.
- **Hardware ASICs** (Coral, Jetson Orin Nano) — 8-15 FPS at 1080p, dead path.
- **Anime sites adding 60fps server-side** — GPU cost > ad revenue, won't happen.

**Only an RTX 4090-class cloud GPU hits 60fps at 1080p reliably** (115-200 FPS at
1080p×2 via TensorRT FP16 per AmusementClub vs-mlrt benchmarks; headroom for 1.5-2
concurrent streams per GPU).

### 1.3 Why we're going single-user MVP not full production

The same 2026-05-24 research agent honest-caveat: nobody publicly runs continuous-
stream NN-VFI as SaaS in 2026. Cloud-RIFE-as-SaaS is either greenfield or a market
that's been tried and doesn't pencil. **Demographic risk is real** (anime fans
haven't been proven to pay $20-40/mo). Rather than burn 5 months on full
production and find out the market doesn't want it, **Abed becomes customer #1,
ships in ~3 weeks, validates the feature is actually good before any commercial
build**. He's stated he personally wants it regardless.

## 2. Architecture

Three components, clean separation:

```
┌─────────────────────────┐       ┌──────────────────────────┐       ┌─────────────┐
│  Laptop                 │       │  Cloud (RunPod RTX 4090) │       │  Chromecast │
│  ─────────────────      │       │  ──────────────────────  │       │  ─────────  │
│  • Browser ext sniffs   │       │  • Worker container      │       │  • Plays    │
│    source HLS URL +     │       │  • Fetches source HLS    │       │    cloud    │
│    cookies/headers      │ HTTPS │    using forwarded creds │       │    HLS URL  │
│  • castbooster proxy    │ ────► │  • NVDEC → RIFE TRT FP16 │       │    via cast │
│    calls orchestrator   │       │    → NVENC               │ ────► │    SDK      │
│  • Orchestrator spins   │       │  • Serves output HLS on  │       │             │
│    RunPod pod or reuses │       │    *.proxy.runpod.net    │       │             │
│  • Receives output URL  │       │  • Idle-watcher self-    │       │             │
│  • pychromecast.play()  │       │    terminates after 10m  │       │             │
│  • Watchdog monitors    │ ◄──── │                          │       │             │
│    for pod death        │       │                          │       │             │
└─────────────────────────┘       └──────────────────────────┘       └─────────────┘
```

**Key property**: laptop is thin orchestrator only. After it tells the Chromecast
which cloud URL to play, laptop can sleep — heavy lifting is between cloud pod and
TV. Saves home bandwidth, no laptop CPU/GPU burn during watching.

**Repos**:
- Existing `Chrome-cast-extension` (this repo) — laptop additions under `app/castbooster/cloud/`
- New `castbooster-cloud-worker` (separate repo) — Docker image + cloud-side code

## 3. Components in detail

### 3.1 Laptop side — new modules under `app/castbooster/cloud/`

```
app/castbooster/cloud/
├── __init__.py
├── runpod_client.py      # RunPod REST API wrapper
├── orchestrator.py       # spin-up + wait-for-ready + return public URL + idle cache
└── cloud_cast.py         # alternative path through _handle_cast: skip transcoder
```

**Decision tree change in `proxy.py::_handle_cast`** (extends P3.4 logic):
```python
if smooth_toggle == ON:
    if hw_tier == "rtx_cuda_capable":   # existing P3.2 path
        spawn local RIFEFilter pipeline
    elif config.cloud_api_key:           # new — single-user MVP
        cloud_url = orchestrator.ensure_pod_and_process(source_url, headers)
        cast.play_media(cloud_url)
    else:                                # default
        passthrough + popup info "smooth not supported on this hardware"
else:
    existing transcoder passthrough
```

**Config**: `.env` in repo root has `CLOUD_API_KEY=<256-bit random>` and
`RUNPOD_API_KEY=<your RunPod key>`. Single-user MVP — these are Abed's keys only.

**Orchestrator state**:
- In-memory cache of `(pod_id, public_url, last_used_ts)` for the current session
- On-disk persistent file `~/.castbooster/cloud_state.json` for orphan termination
  on app restart (defends against laptop crash leaving pods alive)

### 3.2 Cloud worker — Docker image `castbooster/cloud-worker:rife-v4.6-trt-fp16`

```
/app
├── server.py             # FastAPI: /healthz, /process, /stop
├── pipeline.py           # ffmpeg NVDEC → RIFE TRT FP16 → NVENC → HLS subprocess wrapper
├── engines/
│   └── rife-v4.6-trt-fp16-1080p.engine    # pre-built TRT engine, RTX 4090 (Ada)
└── hls_serve/            # static HLS output dir, served by nginx in same container
```

**Runtime stack**:
- Base: `nvidia/cuda:12.6-cudnn-runtime-ubuntu24.04`
- ffmpeg with NVDEC + NVENC enabled (apt: `ffmpeg`, or self-build)
- vs-mlrt for RIFE TensorRT FP16 inference
- nginx serves `/hls/*.m3u8` and `/hls/*.ts`
- FastAPI + uvicorn for the control plane

**Pre-built engine in image (vs. compile-on-cold-boot)**:
- Engine bake during `docker build` step: takes 5-10 min once, ships as a layer
- Pod ready ~10s after boot instead of ~10 min
- Engine is GPU-arch-specific (Ada Lovelace = RTX 4090); ship one variant for v1.
  If RunPod gives us an RTX 5090 (Blackwell) instead of 4090, the engine won't
  load and we fall back to passthrough — acceptable for v1 (RTX 4090 is in stock
  on RunPod Community per 2026-05-24).

**Pipeline operation**:
1. POST `/process` with `{source_url, source_headers, output_resolution}`
2. Spawn ffmpeg subprocess:
   - Input: source HLS via `-headers` with forwarded cookies
   - NVDEC decode (`-c:v h264_cuvid`)
   - vs-mlrt RIFE filter (2x temporal upsample, fp16)
   - NVENC encode (`-c:v h264_nvenc -preset p4 -b:v 8M`)
   - HLS packager (`-f hls -hls_time 4 -hls_list_size 6`)
3. Return `{hls_url: "https://<pod-id>-8080.proxy.runpod.net/hls/playlist.m3u8"}`
4. Idle-watcher thread checks `hls_serve/` mtimes; if no chunks served in 10 min,
   self-terminate (`os.system("runpodctl stop pod")`)

### 3.3 Auth + pod lifecycle

**Auth**:
- 256-bit random `CLOUD_API_KEY` in `.env` (laptop) and set on every pod env at
  spin-up (passed through RunPod API `env` map)
- FastAPI requires `Authorization: Bearer <key>` on `/process` and `/stop`
- `/healthz` is unauth'd (RunPod's own health-check needs to hit it)

**Pod lifecycle**:
1. Laptop's `orchestrator.ensure_pod_and_process(source_url, headers)`:
   - Check in-memory cache for active pod within idle window
   - If exists: POST `/process` to that pod
   - If not: `runpod_client.create_pod(image="...", gpu_type="RTX_4090",
     env={CLOUD_API_KEY: KEY}, ports=[8080])` → returns `pod_id` + `public_url`
   - Poll `GET /healthz` every 2s up to 60s timeout (~25s typical)
   - POST `/process` once healthy
2. Cache `(pod_id, public_url, ts)` in-memory + on disk
3. Idle-watcher in pod self-terminates after 10 min of no chunks
4. Laptop watchdog (separate thread): every 30s, GET `/healthz`. If 3 fails in a
   row → assume pod died/preempted → spin a fresh pod and re-cast (Chromecast
   sees ~25-30s buffering blip — acceptable for v1)
5. On laptop app shutdown: best-effort `runpod_client.terminate(pod_id)`
6. On laptop app start: read `cloud_state.json`, check for orphan pods >6h old, terminate

**Cold start UX**: popup shows "Warming up cloud GPU... ~25s" with a progress
indicator. Subsequent casts within the same 10-min idle window are instant.

## 4. Error handling, failure modes, observability

### 4.1 Failure-mode matrix

| Failure | Detection | Response |
|---|---|---|
| RunPod API down / RTX 4090 out of stock | `create_pod()` errors | Popup "Cloud unavailable, try again". Passthrough cast (no smooth) still works. |
| Pod boots but `/healthz` never responds (60s timeout) | Orchestrator timeout | Terminate bad pod, retry once, then passthrough fallback. |
| Source HLS fetch fails (egydead 503 / geo-block / changed URL) | Pod returns 502 from `/process` | Surface error to popup. User can re-click cast after fixing source. |
| RIFE pipeline crashes mid-stream (NVENC bug / OOM / bad input) | Pod idle-watcher sees no chunks for 30s | Pod self-terminates. Laptop watchdog detects missing chunks on Chromecast → passthrough fallback. |
| Pod preempted by RunPod (rare on Community) | Public URL stops responding | Laptop watchdog spins fresh pod, re-casts. Chromecast buffers ~25-30s. |
| Network drops laptop ↔ cloud | RunPod API timeouts | Exponential backoff retry; if exhausted → popup error + passthrough. |
| Chromecast can't reach cloud HTTPS | pychromecast `play_media()` errors | RunPod pods publish HTTPS via `*.proxy.runpod.net` with public certs. Should Just Work. If not: passthrough fallback. |
| Cost runaway (pod doesn't shut down) | Belt + suspenders: in-pod idle-watcher (primary), laptop orphan-termination on app start (secondary), hard cap on pod lifetime ≤6h (tertiary) | Max wasted: $2.04 per orphan worst-case |

### 4.2 Observability (MVP-light)

- Cloud worker logs to RunPod's built-in log capture (visible in their web UI)
- Laptop side: existing line-numbered log formatter + diagnostic bundle (P3.5
  devtools shipped 2026-05-20)
- **Not adding Sentry yet** — single user (Abed), no other users to crash. When
  opened to others, CLAUDE.md rule #6 (prod-observability) kicks in

### 4.3 Testing strategy

- **Unit tests** — mock RunPod REST API (httpx mock) + mock cloud worker `/process`
  endpoint. Test orchestrator logic for spin-up, reuse, idle-cache, error
  fallback. Pattern matches existing castbooster test style (subprocess +
  monkeypatch)
- **Integration tests** — spin a "fake worker" container locally (no GPU needed)
  responding to `/process` with a pre-canned HLS. Verify E2E laptop → fake-cloud
  → static-HLS → mock-Chromecast
- **E2E acceptance (manual, Abed-driven)** — real RunPod pod + real Chromecast +
  real egydead episode. The "does this actually feel smooth on the TV"
  judgment that no automated test can give

## 5. Scope

### 5.1 In scope for Pillar 3.6 MVP

- Laptop orchestrator module (`app/castbooster/cloud/`)
- RunPod REST client + pod lifecycle (spin/reuse/terminate)
- Cloud worker Docker image (RIFE-v4.6 TRT FP16 on RTX 4090) in a new
  `castbooster-cloud-worker` repo
- FastAPI server + ffmpeg NVDEC→RIFE→NVENC→HLS pipeline
- Integration into existing `_handle_cast` decision tree
- Single-user shared-secret auth
- 6h pod lifetime cap + orphan termination on app start
- Unit + integration tests, manual E2E acceptance

### 5.2 Out of scope (Phase 2 known problems)

| Problem | When it matters | Effort to solve |
|---|---|---|
| **Widevine DRM** (Crunchyroll, Netflix, HiDive) | When opening to paying customers | Significant rework — laptop must do Widevine decryption in browser context, forward raw or re-encoded frames to cloud |
| **Multi-user accounts + billing** | When opening to others | Polar.sh + Convex per CLAUDE.md defaults, ~2-3 weeks |
| **Hot-spare warm pool** (eliminate 25-30s cold start) | When UX matters more than cost | ~$245/mo extra at 24/7 single-pod warm; or RunPod FlashBoot integration |
| **Sentry / prod-observability** | Before opening to anyone but Abed | Per CLAUDE.md rule #6 + prod-observability skill, ~3 days |
| **Pod preempt-resume continuity** | If preempts become annoying | Detect on chunk-stream gap; quick respin; trade-off against cost |
| **Geo-distribution** | If 150ms RTT from Sweden to US is noticeable for cast UX | RunPod has Europe regions; just configure pod region |
| **720p / multi-resolution output** | If bandwidth-constrained | One extra ffmpeg variant in pipeline |
| **Pillar 4 Anime4K** | Separate pillar | Adds upscaling filter to cloud pipeline |

## 8. Decisions log (from brainstorming session 2026-05-24)

- **Scope** → MVP-for-Abed, single user
- **Data flow** → cloud-direct fetch (egydead has no Cloudflare; Crunchyroll DRM is Phase 2 problem)
- **GPU lifecycle** → RunPod on-demand RTX 4090 ($0.34/hr, ~25-30s cold start, ~$41/mo at 4hrs/day)
- **Casting path** → laptop = thin orchestrator, Chromecast plays cloud HLS URL directly
- **Cloud worker stack** → Docker on RunPod, ffmpeg NVDEC/NVENC + vs-mlrt TensorRT FP16
- **Pre-build TRT engine** in Docker image (vs compile-on-cold-boot) → faster cold start
- **Auth** → shared-secret bearer token (single-user MVP), no Polar.sh
- **Module structure** → new code under `app/castbooster/cloud/`, no FilterStage integration (cloud isn't local ffmpeg)
- **Preempt UX** → 25-30s blip on TV acceptable for v1
- **Cost safety** → 6h pod lifetime cap, orphan termination on app start
- **Observability** → MVP-light (RunPod web UI logs + existing castbooster diagnostic bundle); Sentry when opening to others
