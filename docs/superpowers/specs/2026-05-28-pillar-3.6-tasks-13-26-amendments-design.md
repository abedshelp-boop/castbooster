# Pillar 3.6 — Tasks 13–26 amendments + v0.3.1 cloud-worker header passthrough

## Context

The master plan at [`Chrome-cast-extension/docs/superpowers/plans/2026-05-24-pillar-3.6-cloud-vfi-impl.md`](../plans/2026-05-24-pillar-3.6-cloud-vfi-impl.md) was written before the v0.3.0 streaming-fixes ship landed. Six task sections (14–21) need amendments to match current reality:

- **v0.3.0 contract** (shipped 2026-05-28): `/process` returns within 1s with `{hls_url, state, started_at, source_url}` rather than blocking for the encode. New `/process_status` returns `playlist_ready` as the orchestrator's gating signal.
- **RunPod request shape** (corrected by hand during pod ops): `ports: ["8080/http"]` array, `cloudType: SECURE` default, `gpuTypeIds` is a priority list (not a single string), poll `/healthz` directly because RunPod's own `currentStatus` is unreliable.
- **Local interpolation locked dead forever** (Abed 2026-05-28): Cloud is the only smooth path for every user including post-launch. Drops the master-plan-Task-18 "RTX 3090+ local OR cloud" decision tree to "smooth=True → cloud" full stop.
- **Header passthrough required for egydead** (Abed 2026-05-28): MVP must support egydead (his current daily-use platform). v0.3.0 rejects `extra_input_headers` with 400. Need v0.3.1 with an in-pod source-proxy.
- **Real `_handle_cast` integration site** (read from current source): proxy.py's `_handle_cast` is a 200-line orchestrator already integrating with `Transcoder` + `CastManager`. The master-plan-Task-18 helpers (`_play_media_on_chromecast`, `_cast_passthrough`, `_popup_error`) don't exist — the cloud branch must fork inside the real `_handle_cast` between `_build_filter_chain` (decides non-Noop chain) and `Transcoder(...)` spawn.
- **Cloud state schema additions** (for idle-cache + popup reattach): `last_heartbeat`, `idle_until`, `hls_url` alongside `pod_id`, `public_url`, `created_at`.

This document is the canonical record of what those amendments are. The master plan file is also amended inline with `**AMENDED 2026-05-28**` blocks per task, but anyone reading the plan top-to-bottom may skip the originals and follow the amendments.

## Architectural locks (no further negotiation this session)

### Lock 1 — Cloud-only smooth path, forever

When `enable_smooth=True` AND the user is Pro AND the source isn't audio-only AND the source FPS < target FPS, the cloud branch runs. No local-vs-cloud decision tree. No `accel.tier == "nvidia"` check. No `license.vulkan_available()` gate on the cloud path. Reference: project memory [`project_local_interpolation_dead_forever.md`](../../../../.claude/projects/C--Users-Abeds-Cursor-projects-Chrome-cast-extension/memory/project_local_interpolation_dead_forever.md).

The existing local `RIFEFilter` plumbing (in `app/castbooster/filters/interpolation.py`, license.vulkan_available, the local-RIFE leg of `_build_filter_chain`) stays in place — removing it mid-Pillar would destabilize the working passthrough path. Treat as dead code candidates for a later cleanup pillar, not P3.6 scope.

### Lock 2 — Cloud branch forks inside `_handle_cast`, after `_build_filter_chain`, before `Transcoder` spawn

The fork site is [proxy.py:329](app/castbooster/proxy.py) where the existing code calls `_build_filter_chain` then decides whether to spawn `Transcoder`. The cloud branch:

1. Runs only when `_build_filter_chain` returns a non-Noop chain (i.e. all the existing Noop-defaulting conditions are met — Pro, video probed, source FPS < target FPS, etc.).
2. Skips `Transcoder(...)` spawn entirely.
3. Calls `cloud_cast(source_url=loopback_source_url, source_headers=...)` (offloaded via `loop.run_in_executor`).
4. On `result.ok`, calls `cm.play(cast_uuid, result.hls_url, "application/vnd.apple.mpegurl", on_session_end=_make_cloud_on_session_end(orchestrator, pod_id))`.
5. On `not result.ok`, surfaces `info_message="Cloud cast failed: <reason>"`, falls through to the existing passthrough path (no transcoder, raw `/upstream/*` proxy URL fed to Chromecast).

The `_on_session_end` callback for the cloud branch terminates the pod via `orchestrator.terminate_pod(pod_id)` — this is the explicit-stop behavior, with the cloud worker's own 10-min idle_watcher as backstop.

### Lock 3 — `source_url` passed to cloud is the LAPTOP's loopback proxy URL, NOT the raw upstream

The laptop's proxy at `:38123` does cookie replay + UA impersonation + PNG-strip + playlist rewrite. Reusing those means the pod sees clean HLS without the cloud worker needing to reimplement any of it. The cloud worker still gets `source_headers` (Cookie/UA/Referer) because the pod can't reach the laptop's LAN IP — those headers tell the cloud worker's NEW in-pod source proxy (v0.3.1) how to fetch the source itself.

Wait — re-reading: the laptop's proxy is LAN-only. The pod is in a RunPod datacenter. Pod CAN'T hit `http://laptop-lan-ip:38123`. So we CAN'T reuse the laptop proxy from the pod side. The pod has to fetch the source itself, which means it needs the headers.

Correction: `source_url` passed to cloud is the **raw upstream URL** (the egydead `*.m3u8`), and `source_headers` are the Cookie/UA/Referer the laptop's `SessionStore` holds for that session. The cloud worker's v0.3.1 in-pod source proxy applies those headers when fetching.

This is a delta from Lock 3's first wording — sticking with the correction. The PNG-strip + playlist-rewrite logic gets ported to the cloud worker (compactly, ~80 LoC, see v0.3.1 below).

### Lock 4 — Idle-pod lifecycle: explicit terminate on cast-end + 10-min idle_watcher backstop

When Chromecast session ends (`_on_session_end` callback in [proxy.py:440](app/castbooster/proxy.py:440)), the cloud branch calls `orchestrator.terminate_pod(pod_id)` immediately. Cloud worker's idle_watcher (10-min mtime check on `/var/hls`) stays as crash-safety net.

`idle_until` in the state schema is used differently: if the user stops a cast then re-casts within 30s, the orchestrator reuses the pod rather than spinning a new one. Initialize `idle_until = time.time() + 30.0` on `_on_session_end`, terminate only after the grace expires AND no new `ensure_pod_and_process` call has arrived.

### Lock 5 — Polling cadence + budgets

After `POST /process` returns (1s budget), orchestrator polls `GET /process_status` every **1s for 90s** waiting for `playlist_ready=true`. The 90s is the v0.3.0 spec acceptance criterion #2; it covers TRT engine cold-start (~30-60s) plus first-segment write (~10-20s) plus headroom.

If 90s budget exhausts without `playlist_ready`:
1. Terminate the pod (don't leave it running).
2. Surface `CloudCastResult(ok=False, error="playlist never ready in 90s")`.
3. Proxy falls to passthrough with `info_message`.

`healthz_timeout_s=60` (separate from playlist-ready timeout) is the pod-boot budget — how long we wait for `/healthz` to start returning 200 after pod creation. Cold image pull is ~3-6 min on a fresh RunPod node, so this budget might need bumping to 360s for first-time pulls; revisit during Task 23.

### Lock 6 — Cast UI: reuse existing `cast` Native Messaging type

No new `cast_smooth` NM message type (master plan Task 20 invents one). Reuse the existing `cast` message + `enable_smooth=True`. Extend `get_session_status`'s response with cloud-specific fields:

```json
{
  "type": "session_status",
  "state": "<existing transcoder.state>",
  "enable_smooth_actual": <existing bool>,
  "cloud_state": "idle | booting_pod | calling_process | waiting_playlist | streaming | terminated | failed",
  "cloud_warming_s": <seconds since cloud_cast started>,
  "cloud_error": null | "<short>",
  "warnings": [...]
}
```

Popup polls `get_session_status` as it already does; new fields drive a "warmup card" UI.

## v0.3.1 cloud-worker change — in-pod source proxy

### Scope

Add `/source_proxy` endpoint to the cloud worker. Modify `/process` to register a `{source_url, source_headers}` mapping for the lifetime of the pipeline. Modify `run_rife.py` to build the bs source URL as `http://127.0.0.1:8001/source_proxy?token=<token>` instead of passing the raw upstream URL to BestSource.

Reason: BestSource's Python plugin (`bs.VideoSource`) doesn't accept libavformat options — confirmed via context7 (only the C++ API exposes `lavfOpts`). Routing through a local proxy is the cleanest way to inject headers without forking BestSource.

### Endpoint shape

```python
# server.py — additions

@app.get("/source_proxy")
async def source_proxy(token: str, u: str | None = None):
    """Stream the registered source URL (or a child URL extracted from an HLS
    playlist) with the headers the laptop provided in POST /process.

    token: opaque session id registered by /process — gates the proxy from
           external use. We're not strictly authenticated here (the pod is
           supposed to be private behind RunPod's edge), but the token makes
           leak-replay attacks scoped to one /process call.
    u: optional base64url-encoded URL. None = fetch the originally registered
       source_url (playlist root). Set when streaming child URLs from a
       rewritten playlist.
    """
    ...

@app.post("/process", ...)  # modify existing
def process(req: ProcessRequest):
    # ... existing CRLF + headers validation
    headers = req.source_headers or {}
    # NEW: register the source for /source_proxy
    token = secrets.token_urlsafe(16)
    app.state.source_registry.register(token, req.source_url, headers)

    # The pipeline reads from the LOCAL proxy, not the raw upstream.
    local_source_url = f"http://127.0.0.1:8001/source_proxy?token={token}"

    outcome = mgr.start(source_url=local_source_url, headers=None)
    ...
```

### Playlist rewrite

For HLS playlists, the proxy needs to rewrite `#EXTINF` lines pointing at child URLs (variant playlists, segments) to also go through `/source_proxy?token=X&u=<base64>`. Otherwise libavformat dereferences them directly, bypassing our header-injecting proxy.

Implementation ports the existing laptop logic in `app/castbooster/hls_rewriter.py`. Compact form for the pod: ~30 LoC (master + variant playlist rewrite; no need for the laptop's Chromecast-specific URL-shape since the pod is the consumer).

### PNG-strip

Egydead variants (hlswish.com, masukestin.com, audinifer.com) sometimes serve TS segments disguised as PNG. The laptop's `detect_png_ts_wrapper_offset` in [proxy.py:894](app/castbooster/proxy.py:894) handles this. Port the same function to the pod, applied to segment responses before streaming to BestSource.

~30 LoC ported verbatim.
