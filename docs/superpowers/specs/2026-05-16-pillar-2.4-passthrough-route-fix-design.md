# P2.4 Fix — Passthrough Route Regression (Design Spec)

> Patch to the Pillar 2.4 proxy integration. Adds a third LAN-accessible
> namespace `/s/{token}/passthrough/*` so Phase 1 passthrough cast keeps
> working after the `/upstream/*` rename + loopback gate landed.
>
> **Parent docs:**
> - Pillar 2.4 design: [docs/superpowers/specs/2026-05-15-pillar-2.4-proxy-integration-design.md](2026-05-15-pillar-2.4-proxy-integration-design.md) — this spec amends §3.1 D3 and §3.2 steps 3 & 4i.
> - Investigation that surfaced it: `~/.claude/plans/yo-how-are-you-hazy-dahl.md`.

---

## 1. Context

The Pillar 2.4 spec contains an internal contradiction that has not yet
been exercised at runtime, because the user's running Cast Booster
process is from before the `cd72438` rename commit. Once they restart
from current HEAD, every Phase 1 passthrough cast against a real
Chromecast will be 403'd:

- **§3.2 steps 3 and 4i** build the Chromecast playback URL as
  `http://{lan_ip}:38123/s/{token}/upstream/{cosmetic-suffix}`.
- **§3.1 D3 (loopback gate)** wraps every `/upstream/*` route in
  `_require_loopback`, which returns `403 "loopback only"` when
  `request.remote` is not `127.0.0.1` / `::1`.

So the URL the desktop app hands to the Chromecast points at a route
that explicitly rejects the Chromecast's LAN IP. The two design
decisions can't both hold.

Today's investigation found three real failed casts (logged in
`castbooster.log` at lines 2305 / 2384 / 2436). None of them tripped
this bug because the running process is pre-rename. The bug is latent
and will fire the moment the user restarts the app to test their own
Pillar 2.4 work — at which point passthrough cast (the D1 "user always
sees their video" fallback) silently breaks.

---

## 2. Decision

| # | Decision | Choice | Rationale |
|---|---|---|---|
| F1 | How to expose passthrough to the LAN | **Third namespace `/s/{token}/passthrough/*`** | Security policy stays encoded in URL structure: `/upstream/*` = ffmpeg-only, `/output/*` = transcoded Chromecast, `/passthrough/*` = unfiltered Chromecast fallback. Auditable by URL alone; no dynamic state in the gate. |
| F2 | Handler reuse | Reuse `_handle_entry` / `_handle_fetch` via factored inner + two thin wrappers | The handler body has been battle-tested for two months. Only the gate's placement changes. |
| F3 | Phase 1 passthrough security posture | LAN-accessible **by design** — accepted | Confirmed in clarifying question 2026-05-16. Passthrough has no ffmpeg gatekeeper between Chromecast and the cookie/Referer/UA proxy. That's inherent to Phase 1, not a regression. D1 "user always sees their video" depends on this remaining production-viable. |

Options considered and rejected:

- **Relax `_require_loopback` for `sess.passthrough_only=True`.** Couples
  security policy to dynamic state — same URL behaves differently per
  session. A bug flipping `passthrough_only` would unlock the cookie
  proxy LAN-wide. Breaks the D3 "only ffmpeg-on-loopback is a legitimate
  client" invariant.
- **Unify on `/output/*`, fall back to live proxy inside the handler.**
  Conflates "transcoder output" with "raw passthrough" in a single
  namespace. `/output/*` currently accepts only HLS suffixes; would need
  to grow to manifest.mpd / video.mp4 / video.webm support to handle
  passthrough's polymorphism. Handler complexity rises faster than the
  benefit of a unified URL.

## 3. Architecture

### 3.1 Route map (after this fix)

| Namespace | Loopback gate | Handler | Purpose |
|---|---|---|---|
| `GET /s/{token}/upstream/master.m3u8` (and `.mpd` / `.mp4` / `.webm` / `/video`) | **YES** | `_handle_entry_loopback` → `_require_loopback` → `_handle_entry_inner` | ffmpeg subprocess input. Cookie / Referer / UA proxy. Token leak ≠ LAN exploit. |
| `GET /s/{token}/upstream/fetch` | **YES** | `_handle_fetch_loopback` → `_require_loopback` → `_handle_fetch_inner` | ffmpeg subresource fetches. |
| `GET /s/{token}/passthrough/master.m3u8` (and `.mpd` / `.mp4` / `.webm` / `/video`) | NO | `_handle_entry_lan` → `_handle_entry_inner` | **NEW.** Chromecast Phase 1 fallback. Same body as the loopback variant, no gate. |
| `GET /s/{token}/passthrough/fetch` | NO | `_handle_fetch_lan` → `_handle_fetch_inner` | **NEW.** Chromecast subresource fetches in passthrough mode. |
| `GET /s/{token}/output/master.m3u8` / `output/variant.m3u8` / `output/seg_NNNNN.ts` | NO | `_handle_output_manifest` / `_handle_output_segment` (unchanged) | Chromecast transcoded mode. Served from disk. |
| `OPTIONS …` (each above) | per-route | `_handle_options` | CORS preflight. |

`aiohttp` matches literal segments before dynamic; `/upstream/`,
`/passthrough/`, and `/output/` differ in their first literal segment
after the dynamic token, so there's no ambiguity.

### 3.2 Code changes in [app/castbooster/proxy.py](app/castbooster/proxy.py)

1. **`_passthrough_playback_url` (line ~91):**
   ```python
   url = f"http://{lan_ip}:{PROXY_PORT}/s/{sess.token}/passthrough/{path_seg}"
   ```
   Old `/upstream/` segment becomes `/passthrough/`. Function name and signature unchanged.

2. **`_handle_entry` refactor:**
   - Rename the existing function body to `_handle_entry_inner(request)`.
   - Add `_handle_entry_loopback(request)` that calls `_require_loopback` first, then `_handle_entry_inner`.
   - Add `_handle_entry_lan(request)` that calls `_handle_entry_inner` directly.
   - Same refactor for `_handle_fetch` → `_handle_fetch_inner` / `_handle_fetch_loopback` / `_handle_fetch_lan`.

3. **`_build_app` route registration (line ~746):**
   - `/upstream/*` routes: bind to `_handle_entry_loopback` / `_handle_fetch_loopback`.
   - New `/passthrough/*` routes (mirror of `/upstream/*`'s five suffix paths + `fetch`): bind to `_handle_entry_lan` / `_handle_fetch_lan`. OPTIONS preflight for each.

No other handler logic changes. `_proxy_fetch`, `_cookies_for_host`,
`_build_upstream_headers`, `_looks_like_playlist`, `_is_playlist_body`,
`_infer_segment_content_type`, `_CORS_HEADERS` — none touched.

## 4. Out of scope

- Cookie-host filter fix (PR #2). Even after this fix, casts against
  hosts where the captured cookies don't match the upstream CDN host
  will still fail. That's the separate "cookies=0 at proxy fetch" bug
  surfaced in today's log.
- Anti-bot defenses on pirate / embed streaming sites. Outside Cast
  Booster's scope.
- Pruning transcoder cleanup, reload behavior, etc — unchanged by this
  PR.
- Native messaging or extension-side changes. The extension already
  receives the new playback URL via `_handle_cast`'s response — it
  just relays whatever URL the desktop app builds. No JS changes.

## 5. Risk and rollback

**Risk: low.**
- No new handler logic — purely route plumbing.
- No security boundary change — `/upstream/*` stays exactly as
  loopback-only as before.
- Three failure modes to think about: (a) the wrapper functions wire up
  wrong → caught by the new test_proxy_routes_passthrough tests; (b)
  `_passthrough_playback_url` URL shape change → caught by test_handle_cast
  assertion update; (c) OPTIONS preflight missed for the new paths →
  visible as a CORS error in browser console during cast attempt.

**Rollback**: single PR, revert the commit. Phase 1 passthrough returns
to its (still broken) state but no other behavior changes. `/output/*`
and `/upstream/*` are untouched.
